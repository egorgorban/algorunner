<objective>
Prove the phase's riskiest architecture end-to-end first: the ordering contract that makes live streaming correct (API-04) and makes late connections see the current state (API-05).

1. Tracer (Task 1). One status write through `storage.update_task_status` commits to Postgres, publishes a `StatusEvent` to `task:{task_id}:status`, and a WebSocket client on `WS /api/v1/tasks/{task_id}/events` receives the snapshot then the event. It is proven against real Postgres and Redis through a real uvicorn server.
2. Expansion (Task 2). Every other status writer publishes the same way, `updated_at` becomes strictly monotonic per task, and the relay's guarantees (no duplicate, no stale event, snapshot refresh on clarification and terminal states, terminal close, disconnect cleanup, malformed-message tolerance) get their own tests.

Purpose: success criterion 1 of ROADMAP Phase 4 rests on this ordering. The frontend (04-03+) becomes a renderer of snapshot + deltas only once this contract is stable.
Output: the `realtime` module, publish-on-write in `storage/tasks.py`, the WS relay route, the same-loop uvicorn test fixture, and the tests.
</objective>

- **Monotonic updated_at (planner addition):** `now()` is the statement start time, so a writer that waited on the row lock could commit with an earlier timestamp than the write it waited for, and the relay would then forward a status that is not the row's final state. `GREATEST(clock_timestamp(), updated_at + 1 µs)` removes that case without a schema change. It is compatible with the user-resolved order (Postgres first, publish second; dedupe on `timestamp <= snapshot.updated_at`).
- **D-03 extension:** events carry `type: "status"` in addition to `{status, timestamp}` so one socket can carry D-02 snapshots too. No context fields (approach index, iteration, error detail) are added.
