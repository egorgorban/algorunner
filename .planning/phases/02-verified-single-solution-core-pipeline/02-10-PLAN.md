## Design decisions (planner-made; the review leaves the mechanism open)

**CR-01 mechanism: keep the worker as root, drop each CHILD to uid/gid 65534 (nobody).** Chosen over "make the whole worker non-root" because a non-root worker cannot setuid a child to a different uid without CAP_SETUID (Docker grants added capabilities only to the bounding set of non-root processes), and a child with the SAME uid as the worker can read `/proc/<worker pid>/environ` — which is the whole vulnerability. The key stays where it is (root-owned `/proc/<pid>/environ` of the worker and of PID 1, mode 0400 root); the child simply cannot open it. Concretely:

1. The drop uses `asyncio.create_subprocess_exec(..., user=65534, group=65534, extra_groups=[])`. Verified in CPython's `_posixsubprocess.c`: in the forked child the order is setsid, setgroups, setregid, setreuid, THEN `preexec_fn`, THEN exec. That order is load-bearing: `RLIMIT_NPROC=0` must be set after setreuid, because Linux marks PF_NPROC_EXCEEDED when setuid runs with an already-exceeded NPROC limit and then fails the following execve with EAGAIN. `extra_groups=[]` calls setgroups(0, NULL) so root's supplementary groups are not inherited. `setreuid(uid, uid)` also sets the saved uid, so the child cannot regain root. Using the kwargs (C path, errno-carrying `OSError`) rather than doing setuid inside `preexec_fn` also avoids an opaque "Exception occurred in preexec_fn" failure.
2. The drop is conditional: only when `os.geteuid() == 0`. On the developer's macOS host (euid 501) nothing changes and the suite runs unprivileged.
3. Fail closed in the image: `Dockerfile.worker` sets `ALGORUNNER_REQUIRE_PRIVILEGE_DROP=1`. If someone later adds a non-root `USER`, the euid-conditional drop would otherwise silently no-op and re-open CR-01; with the env flag the executor raises `PrivilegeDropUnavailableError` (loud task failure `UNHANDLED_EXCEPTION`, per D-00f) instead.
4. Filesystem ownership: the per-run temp tree (Python script dir; Go: template copy, `main.go`, `gocache`, `gomodcache`, output binary) is chowned to 65534 by the root worker once, after it is fully populated and before any child starts (so no child-controlled symlink race exists at chown time). Go BUILD also runs as 65534, so `go build` on LLM-authored source is not run as root either; `HOME`/`GOCACHE`/`GOMODCACHE` already point inside the per-run dir.
5. Generated Python runs as `python3 -S`: no site processing, so the venv's site-packages (psycopg, redis, openai, httpx, taskiq, langgraph) are not on `sys.path`. Without this, a uid-65534 child could still `import psycopg` from the worker venv and connect to Postgres with the default compose credentials. The harness uses only `math` and `sys` from the stdlib and does not use the `exit`/`quit` builtins, so `-S` is safe (verified).
6. `no-new-privileges` on the worker service blocks privilege gain through setuid-root binaries present in the base image (su, mount, passwd...). Cheap, one line.

**CR-01 network egress — decision: NOT closed in v1; documented honestly as residual.** Considered and deferred: (a) a uid-owner iptables OUTPUT rule for uid 65534 — the only cheap kernel-enforced control, and the dedicated uid introduced here is what makes it possible, but it needs `cap_add: NET_ADMIN` on the worker, iptables in the image, an entrypoint script and a kernel with the owner match module, none of which can be validated natively and which changes the container's privilege profile (an owner-level security decision); (b) `unshare(CLONE_NEWNET)` — blocked by Docker's default seccomp profile without CAP_SYS_ADMIN; (c) full sandbox (gVisor/nsjail/separate container) — SEC-02/SEC-03, explicitly v2. What IS done: the key is no longer readable (the exfiltration payload is gone), venv client libraries are not importable, and the denylists are extended as a best-effort filter for accidental misuse. This is a PARTIAL mitigation only: `getattr`/`__builtins__["__import__"]` tricks bypass the Python AST check, Go's `os.StartProcess` and dot-imports (`import . "net"`, WR-10b) bypass the Go text scan. Lateral access to postgres/redis with the default compose credentials therefore remains reachable by a determined bypass; that is recorded as an accepted v1 residual and pointed at SEC-02/SEC-03.

**CR-02 mechanism:** one shared `run_in_process_group` in `tools/process.py` owns spawn, `wait_for(communicate)`, timeout-to-None, and a `finally` that hard-kills the whole group (`os.killpg(proc.pid, SIGKILL)`, pgid == pid because of `start_new_session`) whenever `proc.returncode is None`, then reaps with a bounded wait. Because it is a `finally`, it covers `CancelledError` (global timeout, shutdown), `TimeoutError` and any other exit path, for the Go build step and the Go run step alike (both call the same helper). No graceful-terminate phase: generated code has no cleanup duty, and a sleep inside the cancel path would itself be a cancellation point. Go run gets CPU/NOFILE/AS rlimits via `preexec_fn`; NPROC is excluded for Go (its runtime creates threads). `worker/tasks.py` needs no edit: verified during planning with a real LangGraph graph (InMemorySaver checkpointer) that `wait_for` cancellation reaches the node coroutine as `CancelledError`, so the executor-level `finally` is the complete fix; the new budget test proves it through the real `_invoke_with_budget`.
