<objective>
Close the correctness gap 02-05 discovered: the Python and Go execution harnesses treated each test's `input`/`output` as an EXPRESSION in the target language, but the Test Generator only saw `code_python` and wrote LeetCode prose, and the Code Generator never fixed a function name. Real LLM output therefore could not run reliably through either harness — the only end-to-end test passed because it used a hand-written scalar `double(n)`. Because Core Value is "correctness verified by actually executing generated code", the Reviewer (02-06) must not be built on a pass/fail signal that can be caused by a harness/format mismatch.

Purpose: CODE-01/02/03/04 and EXEC-01/02 — a stable entry point (function name and typed signature) fixed by the Code Generator for BOTH languages; language-neutral structured test cases (JSON args/expected typed against that signature) produced by the Test Generator; provided examples still always included as ground truth (D-10) after being converted to the structured form; and per-language renderers that turn the same structured cases into valid, typed test programs for the unchanged executors (D-00c, EXEC-03).

Output: a closed language-neutral type vocabulary, `EntryPoint`/`StructuredCase` contracts on `Solution`, an example-to-structured-case converter, `graph/harness.py` renderers (Python + Go, including Go typing and import injection), the Code Generator and Test Generator switched to the new contract, `graph/build.py` execute nodes delegating to the renderers, and end-to-end proof through real `python3` and real `go build` with non-trivial fixtures (Two Sum; list[str] to str).

Format decisions (documented defaults resolved here, not blocking checkpoints):
- F1 Entry point owner: the Code Generator declares it (it already produces both implementations); a deterministic Python check confirms both code strings really define it. It rides in `Solution.entry_point`, so it is persisted with the result and available to the Reviewer and the Phase 3 editorial.
- F2 Closed type vocabulary: `int`, `float`, `bool`, `str`, `list[T]` (nested). Anything else cannot be declared and fails loudly (D-00f). Go maps to `int`, `float64`, `bool`, `string`, `[]T`.
- F3 JSON text at the LLM boundary: OpenAI strict structured outputs cannot express an arbitrary JSON value, so generated cases carry `args_json` (a JSON array, one element per parameter in order) and `expected_json` as STRINGS; Python parses and validates them against the declared types. The durable `StructuredCase` stores native JSON values.
- F4 Provided examples (the decision the gap requires): deterministic-first. LeetCode-style `name = value, name = value` input with a strict-JSON output is parsed in Python with no LLM (highest fidelity, D-10 "as-is"). Any example that does not parse is normalized by the SAME single Test Generator LLM call (extra `normalized_examples` field) and then verified in Python: exact index coverage, declared-type validation, and equality with the example's output whenever that output is strict JSON. No new graph node, no new checkpoint.
- F5 Oracle independence: the Test Generator no longer receives the implementation; expected values come from the problem statement, analysis and signature only, so a bug in the code under test cannot leak into its own oracle.
- F6 `unordered_result` (declared by the Code Generator from the problem statement) compares the top-level list as a multiset; everything else is exact (ints strict, floats within tolerance, nil equals empty slice).
- F7 Harness ownership: all source-string rendering (including the Go import injection formerly private to `graph/build.py`) moves to `graph/harness.py`; `graph/build.py` keeps only thin node wrappers.
- F8 Go executor timeout: `execute_go_node` passes `timeout_s=30.0` (applies to build and run independently). A fresh-cache `go build` of the harness was measured at about 3 seconds locally; the 10-second default leaves too little margin on a CPU-limited container, and a spurious timeout on a correct solution would be a false verification failure.

Structure note: Task 1 is the thin proof of the format (new pure modules, existing behavior untouched, suite stays green, real executors exercised). Task 2 is an intentionally ATOMIC switchover: changing `Solution`'s shape is breaking for the Code Generator, Test Generator, execute nodes and every fixture that constructs them, and splitting it would leave the graph integration tests red between commits — its many small edits (nine files) are a consequence of that, not of scope width. Task 3 hardens with segment-level end-to-end tests that call the real nodes in sequence (not a compiled graph), so they stay valid when 02-06/02-07 restructure the graph.
</objective>
