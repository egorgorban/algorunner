### Locked Decisions

**Architecture (already locked — carried forward from PROJECT.md / interview.md, not re-discussed)**
- D-00a: Hybrid architecture — fixed LangGraph `StateGraph` handles state/transitions; LLM reasoning is bounded to specific nodes (Analyzer, Strategist, Solver, Reviewer, Editorial Writer), not a free supervisor-driven LLM-to-LLM router.
- D-00b: Solution generation uses Strategist + generic Solver: Strategist proposes N tagged approaches, a single generic Solver elaborates each into a concrete algorithm. No dedicated agent per algorithm type.
- D-00c: Deterministic execution lives as **tools** (`PythonExecutorTool`, `GoExecutorTool`), not agents — swappable from subprocess → sandbox later without touching agent code (EXEC-03).
- D-00d: Reviewer returns a structured `ReviewResult` (passed, issues, severity, required_changes) covering correctness, algorithm soundness, edge cases, complexity claim (with reasoning justification), and code quality.
- D-00e: Correction loop is bounded by a configurable `max_iterations` (3-5); exceeding it yields a terminal `FAILED` result, never an unbounded loop.
- D-00f: OpenAI timeout/rate-limit errors are handled via pause-and-cooldown retry with backoff; other reliability failures (malformed structured output, generated-code failure) surface as errors rather than silent retries.
- D-00g: Empirical/runtime verification of claimed asymptotic complexity is explicitly out of scope — Reviewer checks complexity analytically only.

**Clarification Flow**
- D-01: Clarification question is a single free-text natural-language question generated by the Analyzer (not a structured list of missing fields).
- D-02: Multiple clarification rounds allowed, capped at **2 rounds**.
- D-03: The clarification question is exposed via a **separate dedicated endpoint** (`GET /api/v1/tasks/{task_id}/clarification`), distinct from the existing `POST /api/v1/tasks/{task_id}/clarification` answer endpoint (API-03).
- D-04: If still ambiguous after the 2-round cap, the pipeline **proceeds with a stated assumption** rather than failing. The assumption is recorded on the task/artifact for Phase 3's Editorial Writer (EDIT-06).

**Correction Loop Scope**
- D-05: On failed review, only the **targeted** work implied by the issue is regenerated (e.g. algorithm-soundness → Solver; code-quality-only → just Code Generator) — not always Solver → Code Generator → Test Generator wholesale. **Reversibility: costly** — bakes issue-type → node routing into conditional edges.
- D-06: Each correction iteration carries **full history** — all prior attempts and all prior `ReviewResult`s — not just the most recent failure. Prompt size grows per iteration but is bounded by `max_iterations` (3-5).
- D-07: Reviewer distinguishes **critical vs minor** severity. Only critical issues (correctness, algorithm soundness, edge-case failures) trigger `passed=false` and route to correction. Minor issues (style/quality nits) are recorded in `ReviewResult.issues` but `passed=true` — Phase 3's Editorial Writer surfaces them as caveats.

**Reliability Budgets**
- D-08: Global timeout on total task solve time is **10 minutes**. A task exceeding it terminates as `FAILED` (INFRA-04).
- D-09: OpenAI timeout/rate-limit retries use exponential backoff with a capped retry count (concrete curve is researcher's/planner's call).

**Test Generation Depth**
- D-10: User-provided examples are **always included as-is** in the test set — ground truth, never dropped/overridden.
- D-11: When few/no examples are provided, Test Generator must produce **at least 10 additional generated tests**, including explicit edge cases (empty input, boundary values, duplicates, etc.) — deliberately raised from the offered 3-5 range.
- D-12: Generated tests must explicitly target edge cases per approach, feeding REV-02/EDIT-05.

## Summary

Phase 2 turns the Phase 1 skeleton's single stub node into a real, multi-node LangGraph pipeline that actually solves one algorithm approach end-to-end: Analyzer → Strategist → Solver → Code Generator → Test Generator → PythonExecutor/GoExecutor tools → Reviewer → (bounded, issue-routed) correction loop, with a clarification pause/resume built on LangGraph's native `interrupt()`/`Command(resume=...)` primitives. All of this rides on infrastructure Phase 1 already proved works (Postgres-checkpointed `StateGraph`, taskiq+Redis, the `{code,message}` error shape, the full `TaskStatus` enum) — Phase 2 is additive, not a rewrite of `graph/build.py`'s wiring pattern.

Three findings from this session **correct** the project's own prior research (`STATE.md`, `.planning/research/*`) and materially change how risky certain parts of this phase are:

1. **`recursion_limit` is 10007 by default in the installed `langgraph==1.2.12`, not 25** as `STATE.md`'s blocker note and `PITFALLS.md` assumed [VERIFIED: `.venv/lib/python3.14/site-packages/langgraph/_internal/_config.py:32`, `DEFAULT_RECURSION_LIMIT = int(getenv("LANGGRAPH_DEFAULT_RECURSION_LIMIT", "10007"))`]. With `max_iterations` capped at 3-5 and at most ~6-8 nodes per correction cycle, the graph will never come close to exhausting the recursion budget — this "blocker" is now a non-issue; an explicit `recursion_limit` in the invoke config is still good defensive practice but is no longer load-bearing for correctness.
2. **LangGraph's default `durability` mode for `ainvoke()` is `"async"`, not fully synchronous per-superstep persistence** [VERIFIED: `.venv/lib/python3.14/site-packages/langgraph/pregel/main.py:2705-2712`, `"async": Changes are persisted asynchronously while the next step executes.`]. Because this project's worker-crash-resilience story (`.planning/research/STACK.md`) depends on "resume from the last *completed* node," the worker's `ainvoke()`/resume calls should pass `durability="sync"` explicitly — otherwise a worker crash between two supersteps can lose a just-finished checkpoint write that hasn't landed yet, causing a resumed run to silently re-execute (and re-bill) an LLM call that already completed.
3. **`openai` resolves to `3.18.0` on PyPI today**, not the v1/v2 lines `.planning/research/STACK.md` flagged as an open pin decision [dry-run `uv pip install openai` resolved `openai==3.18.0`, cross-checked against Context7's `/openai/openai-python` official-repo `helpers.md` which still documents `client.chat.completions.parse()` with the same `response_format=PydanticModel` / `message.parsed` / `message.refusal` contract]. Pin `openai>=3,<4` and use `chat.completions.parse()` exactly as documented — do not let this float, and treat the Chat Completions structured-output path as current, not deprecated, despite OpenAI's own docs positioning the newer Responses API as the forward direction.

**Primary recommendation:** Extend `graph/state.py`/`graph/build.py` with a real `TypedDict` state and 7-9 plain-async-function nodes (no `Send` fan-out this phase — see Architectural scoping note below), wire the clarification pause as its own thin `interrupt()`-only node separate from the Analyzer's LLM call, route the correction loop via an `Issue.category` field read by a conditional-edge function (not baked into node logic), and add the Go toolchain to `docker/Dockerfile.worker` via a multi-stage `COPY --from=golang:1.27-bookworm` — none of this exists in the image today.

## Architecture Patterns

### Architectural scoping note — this phase is single-approach, not fan-out

`STRAT-01` requires the Strategist to propose 1+ approaches, and `STRAT-04` requires a generic Solver capable of elaborating "each proposed approach." But the Phase 2 boundary in `02-CONTEXT.md` is explicit: *"producing **one** algorithm approach whose Python and Go code are proven correct... multi-approach curation... [is] Phase 3's job."* `STRAT-02` (deciding which alternatives are worth including) is mapped to Phase 3 in `REQUIREMENTS.md`'s traceability table, and `.planning/research/ARCHITECTURE.md`'s `Send`-based multi-approach fan-out diagram is describing the **project-level** end-state (Phase 3+), not this phase.

**Recommendation:** Design `GraphState.approaches: list[Approach]` now (forward-compatible with Phase 3's fan-out), but have the graph deterministically select **one** approach (e.g. `approaches[0]`, or the Strategist's first/highest-priority tag) and run Solver → CodeGen → TestGen → Execute → Review → correction on that single approach only. Do **not** build `Send`-based parallel fan-out this phase — it is unnecessary complexity for a requirement set that only needs to prove the single-approach path works, and Phase 3 is where multi-approach orchestration is actually in scope.

### Pattern 1: LLM reasoning nodes as thin async wrappers around a per-agent structured-output client

**What:** Every LLM-backed node calls `chat.completions.parse(model=..., response_format=PydanticModel)` via a client obtained from `llm/client_factory.py`, keyed by agent name, and returns a plain dict update to graph state — no LangChain `ChatOpenAI`/`with_structured_output` involved (the project's own `STACK.md` locked in the raw `openai` SDK, not a LangChain model wrapper).

**When to use:** Analyzer, Strategist, Solver, Code Generator, Test Generator, Reviewer — every bounded-reasoning node.

**Example (verified against Context7's `/openai/openai-python` `helpers.md`, official repo docs):**
```python
# llm/client_factory.py
from functools import lru_cache
from openai import AsyncOpenAI
from algorunner.config import settings

@lru_cache
def get_client() -> AsyncOpenAI:
    return AsyncOpenAI(api_key=settings.openai_api_key)

def model_for(agent_name: str) -> str:
    # ORCH-03: per-agent model override, falls back to a default
    return getattr(settings, f"{agent_name}_model", settings.default_model)

# agents/reviewer/node.py
from algorunner.llm.client_factory import get_client, model_for
from algorunner.schemas.review import ReviewResult

async def reviewer_node(state: "GraphState") -> dict:
    completion = await get_client().chat.completions.parse(
        model=model_for("reviewer"),
        messages=build_review_messages(state),
        response_format=ReviewResult,
    )
    message = completion.choices[0].message
    if message.parsed is None:
        raise ValueError(f"Reviewer refused or failed to parse: {message.refusal}")
    result = message.parsed
    return {
        "review": result,
        "review_history": state["review_history"] + [result],  # plain append, not a reducer — see Pattern 4
        "iterations": state["iterations"] + 1,
    }
```

**Retry wrapper (D-09, INFRA-03) — verified `tenacity` 9.1.4 is already installed:**
```python
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_exponential
from openai import APITimeoutError, RateLimitError

@retry(
    retry=retry_if_exception_type((APITimeoutError, RateLimitError)),
    wait=wait_exponential(multiplier=1, min=2, max=30),
    stop=stop_after_attempt(5),
    reraise=True,
)
async def call_structured(client, **kwargs):
    return await client.chat.completions.parse(**kwargs)
```
Apply this wrapper inside `get_client()`'s call sites (or as a decorator on each node's LLM call) — `chat.completions.parse()` does **not** retry `LengthFinishReasonError`/`ContentFilterFinishReasonError`/refusal itself (confirmed via the same `helpers.md` fetch); those are validation failures, not transient errors, and per D-00f should surface as errors, not be silently retried by the same backoff wrapper (only `APITimeoutError`/`RateLimitError` should hit this retry — a malformed-output failure should route into the correction loop instead, or fail the task, not spin here).

### Pattern 2: Clarification pause via `interrupt()` in its own thin node, separate from the Analyzer's LLM call

**What:** The Problem Analyzer node makes its LLM call and returns `{analysis, needs_clarification, clarification_question}` as a normal state update — it does **not** call `interrupt()` itself. A conditional edge routes to a separate `clarification_gate` node (zero business logic) only when `needs_clarification` is true; that gate node's entire body is `interrupt(question)`.

**Why this shape, not "call `interrupt()` inside the Analyzer":** [VERIFIED: `.venv/lib/python3.14/site-packages/langgraph/types.py`, `interrupt()` docstring] *"The graph resumes from the start of the node, **re-executing** all logic."* If the Analyzer's expensive LLM call happened before an `interrupt()` call in the **same** node, every resume (including the D-02 second clarification round) would silently re-run that LLM call — wasted cost and a subtle bug (the re-run might produce a different `needs_clarification` verdict on retry, non-deterministically). Isolating `interrupt()` in its own node means a resume only re-executes that trivial node, not the LLM call.

**Verified resume mechanics:**
- Pause: `result_state = await graph.ainvoke(initial_state, config)` returns a dict containing `"__interrupt__"` (a tuple of `Interrupt` objects — [VERIFIED: `.venv/lib/python3.14/site-packages/langgraph/types.py`, `Interrupt` dataclass has `.value: Any`, `.id: str`]) instead of raising — this is the documented signal to persist the question and stop.
- Resume: `await graph.ainvoke(Command(resume=answer_text), config={"configurable": {"thread_id": task_id}})` — [VERIFIED: `.venv/lib/python3.14/site-packages/langgraph/graph/state.py`, `CompiledStateGraph.ainvoke` signature: `input: InputT | Command | None`] confirms `Command` is a valid first positional argument, matching the official docstring example exactly.

### Pattern 3: Protocol-boundary executor tools with process-group kill and resource limits

**What:** `CodeExecutor` Protocol (already specified in `.planning/research/ARCHITECTURE.md` Pattern 3 — carried forward unchanged, still correct) + concrete `asyncio.create_subprocess_exec`-based implementations that spawn in a new session, apply `resource.setrlimit` via `preexec_fn`, and kill the whole process group on timeout.

**Verified stdlib facts (Context7, `/websites/devdocs_io_python_3_14`):** `asyncio.create_subprocess_exec(program, *args, ..., **kwds)` — *"All other keyword arguments are passed to `subprocess.Popen` without interpretation"* — confirms `preexec_fn` and `start_new_session` both work unmodified under `asyncio`, so the sync-`subprocess` safety-net pattern from `.planning/research/PITFALLS.md` Pitfall 1 ports directly to the required-async shape without a stdlib gap.

```python
# tools/python_executor/subprocess_backend.py
import asyncio, os, resource, signal, tempfile
from pathlib import Path
from algorunner.schemas.execution import ExecutionResult

def _limit_resources():
    resource.setrlimit(resource.RLIMIT_CPU, (5, 5))
    resource.setrlimit(resource.RLIMIT_AS, (512 * 1024 * 1024, 512 * 1024 * 1024))
    resource.setrlimit(resource.RLIMIT_NPROC, (0, 0))       # blocks fork() — no fork bombs
    # deliberately NOT setting RLIMIT_FSIZE=0 (SIGXFSZ on any write incl. stderr — PITFALLS.md Pitfall/"What NOT to Use")

class SubprocessPythonExecutor:
    async def run(self, code: str, tests: str, *, timeout_s: float = 10.0) -> ExecutionResult:
        with tempfile.TemporaryDirectory() as tmp:
            script = Path(tmp) / "solution.py"
            script.write_text(code + "\n\n" + tests)
            proc = await asyncio.create_subprocess_exec(
                "python3", str(script),
                stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE,
                cwd=tmp, start_new_session=True, preexec_fn=_limit_resources,
            )
            try:
                stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=timeout_s)
            except asyncio.TimeoutError:
                os.killpg(os.getpgid(proc.pid), signal.SIGTERM)
                await asyncio.sleep(0.5)
                try:
                    os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
                except ProcessLookupError:
                    pass
                await proc.wait()  # reap — never leave a zombie
                return ExecutionResult(passed=False, stdout="", stderr="timed out", exit_code=-1, duration_ms=int(timeout_s * 1000))
            return ExecutionResult(
                passed=proc.returncode == 0,
                stdout=stdout.decode(errors="replace"),
                stderr=stderr.decode(errors="replace"),
                exit_code=proc.returncode,
                duration_ms=0,  # measure via time.monotonic() around the call in the real impl
            )
```

**Go executor — needs a pre-seeded `go.mod` scaffold** (`.planning/research/PITFALLS.md` Pitfall 3, unchanged/still correct): write the generated code into a temp dir that already contains a checked-in template `go.mod` (fixed Go version, no deps), set `GOCACHE`/`GOMODCACHE` env vars to a writable per-execution path, `go build` to a known binary path, then execute that binary directly under your own process-group control (rather than `go run`) so exactly one PID tree needs to die on timeout.

### Pattern 4: Bounded, issue-routed correction loop with explicit (non-reducer) history accumulation

**What:** `ReviewResult.issues: list[Issue]` where `Issue.category: Literal["algorithm_soundness","correctness","edge_case","complexity","code_quality"]` and `Issue.severity: Literal["critical","minor"]` (D-07). A conditional-edge function — not an LLM, not baked into node logic (Anti-Pattern 2 in `.planning/research/ARCHITECTURE.md`, still correct) — reads `state["review"]` and `state["iterations"]` and returns the next node name.

```python
# graph/routing.py
MAX_ITERATIONS = 5  # upper end of the D-00e "3-5" range; configurable via settings.max_iterations

# D-05's two named examples generalize to this mapping — the exact completeness of this
# table beyond the two examples CONTEXT.md gives is an implementation judgment call,
# see Open Questions #2.
_CATEGORY_TO_NODE = {
    "algorithm_soundness": "solver",
    "correctness": "solver",       # a wrong-output bug is treated as algorithm-level by default
    "edge_case": "solver",
    "complexity": "solver",        # complexity claim mismatch implies the algorithm claim itself is wrong
    "code_quality": "code_generator",
}

def decide_after_review(state: "GraphState") -> str:
    review = state["review"]
    if review.passed:  # D-07: only critical issues can make passed=False
        return "finalize_success"
    if state["iterations"] >= state.get("max_iterations", MAX_ITERATIONS):
        return "finalize_failed"
    critical = [i for i in review.issues if i.severity == "critical"]
    # route to the most-upstream node any critical issue implicates
    target_priority = ["solver", "code_generator", "test_generator"]
    targets = {_CATEGORY_TO_NODE.get(i.category, "solver") for i in critical}
    return next((t for t in target_priority if t in targets), "solver")
```

**History accumulation (D-06) reconciled with the checkpoint-bloat pitfall:** `.planning/research/PITFALLS.md` Pitfall 7 warns against `Annotated[list, add]`-style reducers for large per-attempt fields because they grow *every* checkpoint, unboundedly. D-06 explicitly wants full history kept. These are **not actually in conflict** here: because `max_iterations` bounds the loop to at most 3-5 entries, a plain **overwrite-semantics** list built by each node (`state["attempt_history"] + [new_attempt]`, returned as a normal dict value, not an `Annotated` reducer field) is bounded by construction — no automatic-accumulation reducer is needed or wanted. Use plain fields, not reducers, for `review_history`/`attempt_history`; let the node's own return value do the appending, exactly as shown in Pattern 1's `reviewer_node` example above.

### Pattern 5: Global timeout scoped to active execution, not wall-clock-since-submission

**What:** D-08's 10-minute global timeout must not count time the task spends parked in `awaiting_clarification` waiting for a human — `interrupt()` causes `ainvoke()` to return control to the worker (the taskiq task literally completes), so a human taking an hour to answer costs zero "active" worker time. Wrap each `ainvoke()`/resume call (not the task's total lifetime) in `asyncio.wait_for(..., timeout=remaining_budget)`, where `remaining_budget` is `GLOBAL_TIMEOUT_S` minus an `active_execution_seconds` counter accumulated in the Postgres task row across invocations.

```python
GLOBAL_TIMEOUT_S = 600  # D-08

async def _invoke_with_budget(graph, payload, config, task_id, pool):
    task = await get_task(pool, UUID(task_id))
    remaining = GLOBAL_TIMEOUT_S - (task.active_execution_seconds or 0)
    if remaining <= 0:
        await update_task_failed(pool, UUID(task_id), TaskError(code="GLOBAL_TIMEOUT", message="Solve time budget exhausted"))
        return None
    started = time.monotonic()
    try:
        return await asyncio.wait_for(graph.ainvoke(payload, config, durability="sync"), timeout=remaining)
    except asyncio.TimeoutError:
        await update_task_failed(pool, UUID(task_id), TaskError(code="GLOBAL_TIMEOUT", message="Solve time budget exhausted"))
        return None
    finally:
        await add_active_execution_seconds(pool, UUID(task_id), time.monotonic() - started)
```
This is flagged `[ASSUMED]` as the correct reading of D-08 (see Assumptions Log #A1) — CONTEXT.md doesn't explicitly disambiguate "total task solve time" vs "wall-clock since submission," but counting clarification-wait time against a 10-minute budget would make the clarification feature (D-01/D-02) nearly unusable in practice, so cumulative-active-time is the only reading consistent with both requirements coexisting.

### Anti-Patterns to Avoid
- **Calling `interrupt()` after an expensive LLM call in the same node** — re-executes the LLM call on every resume (see Pattern 2).
- **Using LangGraph reducers (`Annotated[list, add]`) for per-attempt code/test snapshots** — unnecessary given `max_iterations` already bounds the list size; reducers add reasoning overhead (automatic vs explicit accumulation) for no benefit here.
- **Letting an LLM node decide the next node name** — already called out in `.planning/research/ARCHITECTURE.md` Anti-Pattern 1, still fully applicable to the Reviewer → correction routing.
- **Relying on the LangGraph default `recursion_limit`/`durability` without reading this phase's verified findings** — both have non-obvious current-version behavior (10007, not 25; `"async"`, not sync-by-default) that contradicts this project's own prior research documents.

### Pitfall 10 (NEW): `recursion_limit`/`durability` defaults differ from what the project's own prior research assumed

**What goes wrong:** `STATE.md`'s open blocker and `.planning/research/PITFALLS.md` Pitfall 6 both describe `recursion_limit` as defaulting to 25 and needing careful reconciliation against `max_iterations`; separately, `.planning/research/STACK.md` states checkpoint persistence "is default behavior once wired in — no extra flag needed." **Why it happens:** The project's Phase-0/Phase-1 research was written against general LangGraph documentation/community sources before the exact pinned version's behavior was checked against the installed package.

**How to avoid:** Treat this RESEARCH.md's verified findings (10007 default recursion limit; `"async"` default durability) as authoritative over the earlier documents for Phase 2 planning. ### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Prompt injection via `problem_text` (a malicious "problem description" attempting to alter Reviewer/Analyzer behavior) | Tampering | Clearly delimit user content in every prompt template, instruct the model to treat it as data; this is a documented risk in `.planning/research/PITFALLS.md`'s Security Mistakes table, still applicable, not yet mitigated in any existing code |
| Generated code attempting filesystem/network access despite no real sandbox yet (v1 scope) | Elevation of Privilege / Information Disclosure | Basic static denylist before execution (disallow `os`, `subprocess`, `socket`, `shutil` imports in generated Python; restrict generated Go to stdlib only, no `net`/`os/exec`) as a cheap complement to the `resource`/process-group controls — real sandboxing (SEC-02/SEC-03) is explicitly deferred, this is the minimum-viable interim control |
| Resource exhaustion from a runaway/forking generated solution | Denial of Service | `RLIMIT_NPROC=0`, `RLIMIT_CPU`, `RLIMIT_AS`, process-group timeout kill — see Pattern 3, mandatory not optional per Pitfall 1 |
| Fork-bomb or zombie accumulation from ungrouped kills | Denial of Service | `start_new_session=True` + `os.killpg` + explicit `await proc.wait()` reap in a `finally` — see Pattern 3 |

## Project Constraints (from CLAUDE.md)

- **Tech stack:** Python 3.14, LangGraph, OpenAI API (model configurable via env/config with per-agent overrides), `uv` package manager, taskiq+Redis, PostgreSQL, Garage (unused until Phase 3), React+TS (not this phase), Docker Compose. All honored above — no deviation proposed.
- **Code execution:** Python via subprocess, Go via compile+run, both without sandboxing in v1 — Pattern 3 matches this exactly; no sandboxing dependency introduced.
- **Architecture style:** simple modular, not DDD/clean-architecture — the recommended structure (`agents/`, `tools/`, `schemas/`, `llm/`) extends Phase 1's existing flat modular layout, no new layering introduced.
- **Explicit "What NOT to Use" directives honored:**
  - Blocking `subprocess.run()` inside `async def` taskiq tasks → avoided via `asyncio.create_subprocess_exec` (Pattern 3).
  - Bare `psycopg.connect()` without `autocommit=True, row_factory=dict_row` → not touched this phase, existing `storage/postgres.py` pattern reused unchanged.
  - `resource.setrlimit(RLIMIT_FSIZE, (0,0))` → explicitly avoided in Pattern 3's `_limit_resources()`, with the reasoning documented inline in the code example.
  - `subprocess.run(..., timeout=N)` alone (without process-group kill) → avoided via `start_new_session=True` + `os.killpg` (Pattern 3).
  - Treating `chat.completions.parse()` as retry-safe by default → explicit `tenacity` wrapper only around `APITimeoutError`/`RateLimitError`, not around refusal/parse failures (Pattern 1).
- **GSD Workflow Enforcement:** This research was produced under `/gsd-plan-phase`'s research step; no direct file edits were made outside this workflow.
