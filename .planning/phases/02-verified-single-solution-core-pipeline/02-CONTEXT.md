<decisions>
## Implementation Decisions

### Architecture (already locked — carried forward from PROJECT.md / interview.md, not re-discussed)
- **D-00a:** Hybrid architecture — fixed LangGraph `StateGraph` handles state/transitions; LLM reasoning is bounded to specific nodes (Analyzer, Strategist, Solver, Reviewer, Editorial Writer), not a free supervisor-driven LLM-to-LLM router. Product owner explicitly rejected the supervisor variant (interview.md variant B) as "less deterministic, more expensive, harder to debug."
- **D-00b:** Solution generation uses Strategist + generic Solver (interview.md variant B without per-algorithm-type agents): Strategist proposes N tagged approaches (e.g. brute force, optimized), a single generic Solver elaborates each into a concrete algorithm. No dedicated agent per algorithm type.
- **D-00c:** Deterministic execution lives as **tools** (`PythonExecutorTool`, `GoExecutorTool`), not agents — keeps them swappable from subprocess → sandbox later without touching agent code (EXEC-03).
- **D-00d:** Reviewer returns a structured `ReviewResult` (passed, issues, severity, required_changes) covering correctness, algorithm soundness, edge cases, complexity claim (with reasoning justification, not just accepted Big-O notation), and code quality.
- **D-00e:** Correction loop is bounded by a configurable `max_iterations` (3-5); exceeding it yields a terminal `FAILED` result, never an unbounded loop.
- **D-00f:** OpenAI timeout/rate-limit errors are handled via pause-and-cooldown retry with backoff (not immediate failure); other reliability failures (malformed structured output, generated-code failure) surface as errors rather than silent retries.
- **D-00g:** Empirical/runtime verification of claimed asymptotic complexity is explicitly out of scope — Reviewer checks complexity analytically (reasoning-based) only.

### Clarification Flow
- **D-01:** Clarification question is a single free-text natural-language question generated by the Analyzer (not a structured list of missing fields) — matches how a human would ask, and the answer channel is free text anyway.
- **D-02:** Multiple clarification rounds are allowed, capped at **2 rounds**. Round cap is intentionally lower than the correction loop's max_iterations (3-5) since clarification should resolve quickly or fall back.
- **D-03:** The clarification question is exposed via a **separate dedicated endpoint** (e.g. `GET /api/v1/tasks/{task_id}/clarification`), distinct from the existing `POST /api/v1/tasks/{task_id}/clarification` answer endpoint (API-03, already fixed by REQUIREMENTS.md).
- **D-04:** If the problem is still ambiguous after the 2-round cap is exhausted, the pipeline **proceeds with a stated assumption** rather than failing the task. The assumption is recorded on the task/artifact so Phase 3's Editorial Writer can surface it in the article's problem restatement (EDIT-06).

### Correction Loop Scope
- **D-05:** On failed review, only the **targeted** work implied by the issue is regenerated — e.g. an algorithm-soundness issue routes back to the Solver, a code-quality-only issue reruns just the Code Generator — rather than always redoing Solver → Code Generator → Test Generator wholesale. — **Reversibility:** costly — this bakes issue-type → node routing into the graph's conditional edges; switching to "always redo everything downstream" later means restructuring those edges, not just a config change.
- **D-06:** Each correction iteration carries **full history** — all prior attempts and all prior `ReviewResult`s, not just the most recent failure — so the Solver/Code Generator sees the complete pattern of what's been tried and rejected. Prompt size grows per iteration but is bounded by max_iterations (3-5).
- **D-07:** Reviewer distinguishes **critical vs minor** issue severity. Only critical issues (correctness, algorithm soundness, edge-case failures) trigger `passed=false` and route to correction. Minor issues (e.g. style/quality nits) are recorded in `ReviewResult.issues` but the result is still `passed=true` — Phase 3's Editorial Writer can surface them as noted caveats rather than forcing a correction cycle.

### Reliability Budgets
- **D-08:** Global timeout on total task solve time is **10 minutes**. A task exceeding it terminates as `FAILED` (INFRA-04) rather than running indefinitely.
- **D-09:** OpenAI timeout/rate-limit retries use **exponential backoff with a capped retry count** (concrete count/delay curve is Claude's/researcher's call — e.g. `tenacity`'s standard pattern already flagged in `.planning/research/STACK.md`).

### Test Generation Depth
- **D-10:** User-provided examples (from the original problem submission, D-01/D-02 of Phase 1's `examples` field) are **always included as-is** in the test set that runs against generated code — they're ground truth from the problem statement. Test Generator adds more tests on top, it never drops or overrides provided examples.
- **D-11:** When few or no examples are provided, Test Generator must produce **at least 10 additional generated tests**, including explicit edge cases (not just typical-case coverage) — empty input, boundary values, duplicates, etc. (User explicitly raised this minimum from the initially-offered "3-5" range to 10 — a deliberate override, not a default.)
- **D-12:** Generated tests must explicitly target edge cases per approach (not just typical-case coverage) — this feeds directly into EDIT-05 (editorial surfaces edge cases the Reviewer identified as handled) and gives the Reviewer's edge-case check something concrete to evaluate against.

### Claude's Discretion
- Exact `tenacity` retry count and backoff delay curve for OpenAI timeout/rate-limit handling (D-09) — not a product-facing decision, researcher/planner picks concrete numbers.
- `Command` vs `add_conditional_edges` idiom for the correction-loop graph structure — flagged in STATE.md as an actively-evolving part of the LangGraph API; researcher confirms against the pinned LangGraph version.
- Reconciling LangGraph's internal `recursion_limit` (default 25, counts supersteps) against the app-level `max_iterations` (3-5) so a `GraphRecursionError` never leaks through instead of a clean `FAILED` result — technical wiring detail, not a product decision.
- OpenAI Python SDK v1 vs v2 pinning (flagged as an open blocker in STATE.md) — technical dependency decision for researcher/planner.
- Internal Pydantic schema shapes for `ProblemAnalysis`, `Solution`, `ReviewResult`, `Issue`, etc. beyond what's specified above — implementation detail.
- Exact wording/prompt design for the Analyzer's clarification question — implementation detail within the free-text-question decision (D-01).

<specifics>
## Specific Ideas

- Clarification round cap (2) is deliberately tighter than the correction loop's `max_iterations` (3-5) — the user wants clarification to resolve fast or fall back to a stated assumption, not become its own open-ended interrogation loop.
- Test Generator's minimum-test floor was explicitly raised by the user from the offered 3-5 range to **10**, with edge cases required — a stronger correctness bar than the default suggestion, consistent with the project's stated Core Value ("correctness matters more than explanation quality or speed").
- Correction-loop routing is issue-targeted (D-05), which is a more involved implementation than "always redo everything" — the user chose thoroughness/efficiency over simplicity here, consistent with wanting a "production-ready" system per PROJECT.md.

</specifics>
