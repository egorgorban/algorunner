**Root cause (verified by reading the code):** `attempt_consume_clarification` (storage/tasks.py:81-102) runs `UPDATE tasks SET status = %s, updated_at = now() WHERE id = %s AND status = %s RETURNING id` and never touches `clarification_question`. `update_task_clarification` (storage/tasks.py:67-78) is the only writer of that column. `get_clarification_question` (api/routes/tasks.py:38-45) hides the question by gating on `status == AWAITING_CLARIFICATION`; `get_task_status` (api/routes/tasks.py:28-35) has no such gate and returns the raw column via `TaskRecord.clarification_question` (schemas/task.py:67, `str | None = None`, so NULL serializes as JSON null with no schema change).

**Worker path analysis — no worker change needed:** the single atomic-UPDATE fix in the storage helper fully covers the completed/failed case, because a task can only reach completed/failed after consume:
- A pause (`_handle_result_or_pause` on `__interrupt__` -> `update_task_clarification`, worker/tasks.py:57-60) returns without invoking the graph again, so nothing can complete or fail the task while it is parked in awaiting_clarification.
- The resume (`resume_task_with_clarification`) is enqueued by the API strictly after `attempt_consume_clarification` returned True (routes/tasks.py:56-59). Every completed/failed write in the resume path (`_handle_result_or_pause` failed/completed branches, `_invoke_with_budget` GLOBAL_TIMEOUT via `update_task_failed`, the CR-01 exception handler) therefore runs on a row whose question is already NULL.
- A second clarification round goes through `update_task_clarification` again (sets the new question + awaiting_clarification), and its own consume clears it — no worker change.
- `update_task_completed`, `update_task_failed`, `update_task_status`, `get_task`, the routes, and `TaskRecord` stay untouched. Out of scope and NOT addressed: a hypothetical broker redelivery of `solve_problem` for an already-paused task would reset status via `update_task_status` without going through consume; that is a pre-existing, separate concern (unverified whether the broker redelivers acked-after-pause tasks) and no such path exists in the normal flow.

**No DB migration:** the `clarification_question` column already exists as nullable `TEXT` (migrations/0002_add_clarification_columns.sql: no NOT NULL, no default), so writing NULL is legal. The `pg_pool` fixture (tests/conftest.py) applies pending migrations once per session; nothing to add.
