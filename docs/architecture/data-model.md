# Data Model

## Tasks Table

The `tasks` table is the authoritative store for task state. All status reads and writes go here.

### Schema

```sql
CREATE TABLE tasks (
    id UUID PRIMARY KEY,
    status VARCHAR(32) NOT NULL DEFAULT 'queued',
    problem_text TEXT NOT NULL,
    language VARCHAR(2) NOT NULL,
    examples JSONB NOT NULL DEFAULT '[]'::jsonb,
    result JSONB,
    error JSONB,
    clarification_question TEXT,
    active_execution_seconds DOUBLE PRECISION NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Columns

- **id**: UUID primary key, generated by client or server.
- **status**: One of 12 TaskStatus values (see status enum below).
- **problem_text**: Original problem statement (English or Russian).
- **language**: "en" or "ru".
- **examples**: JSON array of {input, output, explanation} objects provided by user.
- **result**: NULL until task completes; then a complex JSON object (see Result Shape below).
- **error**: NULL normally; on FAILED status, contains {code, message} structured error.
- **clarification_question**: NULL normally; non-null when status = awaiting_clarification. Cleared atomically when answer is consumed.
- **active_execution_seconds**: Wall-clock seconds elapsed since task creation. Updated on every status write.
- **created_at**: Task creation timestamp (auto-filled).
- **updated_at**: Last status update timestamp (auto-filled).

### TaskStatus Enum

```python
class TaskStatus(str, Enum):
    QUEUED = "queued"
    ANALYZING_PROBLEM = "analyzing_problem"
    DESIGNING_SOLUTION = "designing_solution"
    GENERATING_CODE = "generating_code"
    GENERATING_TESTS = "generating_tests"
    EXECUTING_TESTS = "executing_tests"
    REVIEWING = "reviewing"
    CORRECTING = "correcting"
    AWAITING_CLARIFICATION = "awaiting_clarification"
    WRITING_EDITORIAL = "writing_editorial"
    COMPLETED = "completed"
    FAILED = "failed"
```


### Result Fields

- **approaches**: Array of approach summary objects, in ascending approach_id order. Each holds the approach name, technique, role, verification status, and iteration count.
- **editorial**: The fully composed Editorial object in Russian (see Editorial Schema below). Null if task failed before Editorial Writer ran.
- **editorial_warnings**: Array of warning codes from deterministic Russian-language checks (e.g., "language_check_failed" if Cyrillic validation failed). Empty if all checks pass.
- **artifact_keys**: List of successfully written artifact keys to Garage, in deterministic order. Enables audit trail.
- **artifacts_incomplete**: Boolean. True if any artifact write failed or was skipped; False if all writes succeeded.

## Editorial Schema

```python
class Editorial(BaseModel):
    title: str
    problem_statement: str
    difficulty: str  # "Easy", "Medium", "Hard"
    techniques: list[str]  # Topic/technique tags from all approaches
    editorial_approaches: list[EditorialApproach]
    notes: str  # Narrative connecting the approaches
```

```python
class EditorialApproach(BaseModel):
    name: str  # "Brute-force", "Optimized", etc.
    technique: str
    intuition: str  # Why this approach works (Russian)
    algorithm: str  # Step-by-step explanation (Russian)
    python_code: str  # Verbatim from Code Generator
    go_code: str  # Verbatim from Code Generator
    complexity: str  # Big-O with one-line justification (Russian)
    edge_cases: list[str]  # From Reviewer's analysis
```

## Error Shape

When task status = FAILED, `error` contains:

```json
{
  "code": "CORRECTION_LOOP_EXHAUSTED",
  "message": "Max iterations (5) reached without a passing review on approach 0"
}
```

Common error codes:
- `CORRECTION_LOOP_EXHAUSTED` — Approach failed after max_iterations
- `GLOBAL_TIMEOUT_EXCEEDED` — 20-minute budget exceeded
- `CLARIFICATION_CAP_REACHED` — Ambiguity remains after 2 rounds
- `GRAPH_RECURSION_ERROR` — LangGraph recursion_limit hit (internal error)
- `UNHANDLED_EXCEPTION` — Unexpected exception during execution

## Garage Artifact Storage

All intermediate artifacts are persisted to Garage (S3-compatible) with the key layout:

```
tasks/{task_id}/
├── analysis.json                      # ProblemAnalysis output
├── approaches/
│   ├── 0/
│   │   ├── iter-1/
│   │   │   ├── solution.json          # Solver output
│   │   │   ├── python_exec.json       # Python executor result
│   │   │   ├── go_exec.json           # Go executor result
│   │   │   └── review.json            # Reviewer result
│   │   ├── iter-2/
│   │   │   ├── ...                    # (if correction loop iterated)
│   │   └── summary.json               # Approach outcome (final status, iterations)
│   └── 1/
│       ├── iter-1/
│       │   └── ...
│       └── summary.json
└── editorial.json                      # Final Editorial object
```

### Key Properties

- **Immutability by design:** Keys include task_id (UUID) and iteration counters, so each invocation produces unique keys. No overwrite semantics.
- **Durability:** Once written, artifacts are kept forever (no retention policy in v1).
- **Write failures:** If a write fails, it is logged as a warning; the task continues and `result.artifacts_incomplete = true` is set.
- **Audit trail:** `result.artifact_keys` lists every successfully written key in deterministic order.

## Redis Usage

### Task Queue

taskiq's `RedisStreamBroker` maintains the task queue as a Redis Stream:

```
Key: algorunner-tasks
Consumer group: algorunner-workers
Message format: Serialized task invocation (task_id, etc.)
```

Properties:
- **Acknowledgement:** Workers acknowledge messages after processing; unacknowledged messages are reclaimed after `unacknowledged_lock_timeout` (30 seconds).
- **Durability:** Stream persists across broker restarts, preventing task loss.

### Status Event Pub/Sub

Worker publishes status transitions to a Pub/Sub channel:

```
Channel: task:{task_id}:status
Message: JSON StatusEvent
{
  "status": "generating_code",
  "timestamp": "2026-09-25T11:05:23.456Z"
}
```

Properties:
- **Publish-after-commit:** Worker writes Task.status to Postgres, then publishes to Redis. Ensures eventual consistency.
- **Subscription-before-snapshot:** WebSocket handler subscribes to the channel before querying Postgres, avoiding a race.
- **No persistence:** Redis pub/sub is fire-and-forget; if no subscriber is listening, the message is lost (not an issue because WebSocket clients subscribe immediately).

## LangGraph Checkpoints

LangGraph uses `AsyncPostgresSaver` to persist execution state across node boundaries. Tables are created automatically on first use:

```sql
-- Automatically created by AsyncPostgresSaver.setup()
CREATE TABLE checkpoint_migrations (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL UNIQUE,
    executed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE checkpoints (
    thread_id VARCHAR(255) NOT NULL,
    checkpoint_id VARCHAR(36) NOT NULL,
    checkpoint BYTEA NOT NULL,
    metadata BYTEA,
    PRIMARY KEY (thread_id, checkpoint_id)
);

CREATE TABLE checkpoint_blobs (
    thread_id VARCHAR(255),
    channel VARCHAR(255),
    version_number INTEGER,
    blob BYTEA NOT NULL,
    PRIMARY KEY (thread_id, channel, version_number)
);
```

### Usage

- **thread_id**: Set to the task_id (UUID) so each task has its own checkpoint sequence.
- **checkpoint_id**: Auto-generated by LangGraph; represents a superstep counter.
- **Checkpoint resumption:** When a task is resumed (e.g., after clarification), the worker re-invokes the graph with the same thread_id, and LangGraph loads the latest checkpoint and continues from there.

## Type Safety

All data crossing API/worker boundaries is validated by Pydantic models:

- **TaskRecord** — task lifecycle (id, status, timestamps)
- **ProblemAnalysis** — analyzer output
- **Approach, Solution** — strategist, solver outputs
- **ExecutionResult** — executor tool outputs
- **ReviewResult** — reviewer output
- **Editorial, EditorialApproach** — editorial writer output

These schemas are imported and used identically in both the API process and the worker process, ensuring consistency.
